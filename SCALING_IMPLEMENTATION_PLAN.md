# Scaling Optimizations Implementation Plan

This plan details the necessary steps to scale the Gully Predict application, focusing on frontend lazy loading, database indexing, Redis caching, and asynchronous task queues.

## User Review Required

> [!WARNING]
> **Infrastructure Requirements**
> Implementing Redis and Celery will require additional infrastructure. When deploying, you will need to provision a Redis instance (e.g., AWS ElastiCache, Google Cloud Memorystore, or a managed Redis add-on like Upstash). Please confirm if you are okay with adding Redis as a dependency.

## Open Questions

> [!IMPORTANT]
> **Celery vs. BackgroundTasks:** Currently, the backend uses `APScheduler`. Switching to Celery provides robust task queuing but adds complexity. Do you want to go full Celery, or use FastAPI's built-in `BackgroundTasks` combined with `APScheduler` for a simpler approach? (Since we are adding Valkey, Celery is now easily supported if you want it).

## Proposed Changes

---

### Frontend

Currently, all pages in `App.tsx` are imported synchronously, which leads to a large initial JavaScript bundle. We will implement React's `lazy` and `Suspense`.

#### [MODIFY] [App.tsx](file:///Users/rasheed/Documents/git/gully-predict/frontend/src/App.tsx)
- Replace static imports for page components (e.g., `Hub`, `MatchCenter`, `Leaderboard`) with `React.lazy(() => import('./pages/PageName'))`.
- Wrap the `<Routes>` block in a `<Suspense fallback={<LoadingSpinner />}>` boundary to handle loading states seamlessly.

#### [MODIFY] [vite.config.ts](file:///Users/rasheed/Documents/git/gully-predict/frontend/src/vite.config.ts)
- Fine-tune `workbox` caching rules to ensure static assets (JS/CSS chunks generated by lazy loading) are cached effectively by the Service Worker for offline and fast-reload capabilities.

---

### Backend: Database & Caching

#### [MODIFY] [models.py](file:///Users/rasheed/Documents/git/gully-predict/backend/models.py)
- Review and add explicit `Index` definitions for high-frequency query paths. 
- E.g., compound index on `LeaderboardEntry` `(league_id, points DESC)` to speed up leaderboard fetching.
- Ensure `CampaignResponse` has indices on `(campaign_id, match_id)` to speed up the scoring engine.

#### [MODIFY] [backend/utils/cache.py](file:///Users/rasheed/Documents/git/gully-predict/backend/utils/cache.py)
- Replace the existing in-memory `SimpleCache` with a Redis/Valkey client connection manager using `redis.asyncio` configured to connect to Aiven for Valkey.
- Update the existing caching helper functions (`get`, `set`, `invalidate`) to use the Valkey client, ensuring the API routers that currently import `backend_cache` continue to work seamlessly.

#### [MODIFY] [leaderboard_router.py](file:///Users/rasheed/Documents/git/gully-predict/backend/router/leaderboard_router.py) & [match_router.py](file:///Users/rasheed/Documents/git/gully-predict/backend/router/match_router.py)
- Wrap the main GET endpoints (e.g., fetching the global leaderboard) with Redis caching logic. The cache will be set to expire every 1-5 minutes, drastically reducing database load.

---

### Backend: Asynchronous Tasks

#### [MODIFY] [scheduler.py](file:///Users/rasheed/Documents/git/gully-predict/backend/scheduler.py) / [NEW] `tasks.py`
- If moving to **Celery**: Initialize a Celery app configured with the Redis broker. Move `auto_predict_daily_job` and match scoring functions into Celery `@task` definitions.
- If using **FastAPI BackgroundTasks** (simpler): Refactor the endpoint that triggers scoring to accept a `BackgroundTasks` object, so the scoring loop runs outside the request-response cycle, preventing timeouts.
